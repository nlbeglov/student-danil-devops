## 5. Проверка за 5 минут
Действия (на VPS, каталог `/opt/devops/task05`):
1. `./scripts/check.sh push`: исходное состояние стенда.
2. `./scripts/fault.sh proxy` (либо `database`, либо `readonly`): внести сбой.
3. `./scripts/check.sh`: убедиться, что сбой заметен (502).
4. Диагностика: `cd configs && docker compose logs --tail 20 caddy` (для `database` и `readonly` смотреть `logs server`).
5. `./scripts/recover.sh`, затем `./scripts/check.sh push`.

Ожидаемый результат:
- шаг 1: «все проверки пройдены», в выводе hash `92f9bf1592d4a5cc45e90767164ac03f97a3c8a5` и сумма `check.txt` `7e7733ff…bef29`;
- шаг 3: HTTPS, вход и clone дают 502;
- шаг 4: причина видна в логах (`connection refused` на `server:3001`, либо `no such host` для `postgres-db`, либо `Read-only file system`);
- шаг 5: все проверки снова проходят, новый push выполняется, исходный коммит и сумма `check.txt` не изменились.

## Проблемы и ограничения
- В процессе развёртывания Caddy не мог выпустить сертификат: у VPS нет рабочего IPv6, а в контейнер попал IPv6-адрес DNS. Исправлено блоком `dns` (1.1.1.1, 8.8.8.8) в сервисе `caddy`.
- После правки `docker-compose.yml` контейнер Caddy пришлось пересоздать (`--force-recreate`): порты 80/443 не были опубликованы.
- Проверка «анонимный clone отклонён» сначала давала ложный провал из-за сохранённых учётных данных git (credential helper); в `lib.sh` credential helper'ы отключены.
- Закрытость портов 3000 и 5432 проверена реальным запросом с таймаутом: `nc -zv` показывает «succeeded» из-за особенностей сети, хотя ответа сервиса нет.
- Время диагностики определено по журналу `faults.log` (от внесения сбоя до начала восстановления) и приблизительное, поскольку включает паузы на запись выводов.
