# Требование 5
> После исправления каждого сбоя проверить HTTPS, вход пользователя, clone, наличие исходного коммита в истории и контрольную сумму check.txt. Затем выполнить новый push с добавлением другого файла. Сохранить тома, историю и ограничения доступа. После каждого опыта возвращать стенд в рабочее состояние.

## Порядок проверки после каждого исправления
После `./scripts/recover.sh` в каждом опыте выполнялась одна и та же команда, вывод сохранялся в журнал «после»:
```
./scripts/check.sh push | tee evidence/incident-N-after.txt
```
Она проверяет: HTTPS и редирект, закрытый репозиторий без авторизации, вход `review-user`, clone, наличие исходного коммита в истории, SHA-256 `check.txt`, новый push (отдельный файл), а также неизменность эталонной конфигурации.

Эталон ([baseline.txt](baseline.txt)):
- полный hash коммита: `92f9bf1592d4a5cc45e90767164ac03f97a3c8a5`
- SHA-256 `check.txt`: `7e7733ff0982d931645c43e95712b0ae5e0eae27993a1815913d23fa42fbef29`

## Сохранность томов, истории и ограничений доступа
- **Тома и история не пересоздавались.** Данные хранятся в bind-mount `data/gitea` и `data/postgres`; `recover.sh` пересоздаёт только `server` и `caddy`, команда `down -v` не используется. Контейнер БД за все три опыта не пересоздавался (в журналах `db` стабильно «Up 35 hours», затем «Up 37 hours», создан 43–45 часов назад).
- **История неизменна.** После каждого опыта исходный коммит на месте, SHA-256 `check.txt` совпадает с эталоном; новые push-коммиты добавляются поверх.
- **Ограничения доступа сохранены.** После каждого исправления анонимный API отвечает 404, анонимный clone отклоняется, регистрация остаётся закрытой.

## Возврат стенда в рабочее состояние
После каждого опыта стенд возвращался `recover.sh` (время начала и конца — в [faults.log](faults.log)); в журналах «после» первая проверка показывает `запущено 3 из 3`, а в заголовке `внесённый сбой: нет`.
