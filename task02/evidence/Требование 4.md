# Требование 4
## 1. Проверка `/health` и `/version` после доставки
Шаг `Verify deployment` в [.github/workflows/ci-cd.yml](../.github/workflows/ci-cd.yml) выполняется автоматически в конце каждого успешного деплоя:
```
sleep 30
curl -sf "https://${APP_DOMAIN}/health"
curl -sf "https://${APP_DOMAIN}/version"
```
`curl -sf` возвращает ненулевой код завершения при HTTP-ошибке или обрыве соединения — это и приводило к «красному» прогону CI/CD #2 (см. [Требование 5](<Требование 5.md>)), пока проверку не заменили ретраями в CI/CD #3.

Ручная проверка (снято на VPS после деплоя `83a3acd`):
```
curl -s https://test0.politblocks.com/health; echo
curl -s https://test0.politblocks.com/version; echo
```
```
{"status":"ok"}
{"version":"83a3acd55071798f0c6dbe84d1a3697f86bd6ed5"}
```
## 2. Digest предыдущего успешного выпуска
Ничего специально не «сохраняется» отдельным файлом — GHCR хранит все опубликованные версии образа постоянно (https://github.com/nlbeglov/nerp-test-task02/pkgs/container/nerp-test-task02), а лог каждого прогона `build` печатает свой digest шагом «Print image reference». Этого достаточно, чтобы в любой момент найти digest нужного предыдущего релиза и передать его в `Rollback` (см. [Требование 6](<Требование 6.md>)) — что и было проверено на практике.
## 3. Исключение одновременных доставок
```yaml
concurrency:
  group: deploy-production
  cancel-in-progress: false
```
Одна и та же группа `deploy-production` указана и в `ci-cd.yml`, и в `rollback.yml` — GitHub Actions не даст запустить второй `deploy`/`rollback`, пока не завершится текущий (новый запуск встаёт в очередь, `cancel-in-progress: false` не отменяет уже идущий).
## 4. Секреты в CI/CD
Repository → Settings → Secrets and variables → Actions:

| Секрет | Назначение |
|---|---|
| `VPS_HOST` | адрес сервера (`144.31.119.139`) |
| `VPS_USER` | пользователь SSH (`root`) |
| `VPS_SSH_KEY` | приватный ключ отдельной пары, сгенерированной для CI (`ssh-keygen -t ed25519 -C "github-actions-task02" -f ~/.ssh/task02_deploy_key`, публичная часть добавлена на VPS через `ssh-copy-id`) |

`GITHUB_TOKEN` для логина в GHCR отдельно не заводится — используется встроенный токен, автоматически выдаваемый на каждый запуск workflow. Сами значения секретов нигде в репозитории, логах и в этом отчёте не публикуются — в `scripts/ci-deploy.sh` приватный ключ пишется во временный файл с правами `600` и удаляется в конце скрипта (`rm -f "$SSH_KEY_FILE"`).

## 5. Доработки после выпуска 83a3acd (в CI ещё не прогонялись)
Фактические прогоны выше сделаны со старой версией workflow. После них в репозиторий внесены изменения, закрывающие замечания к пунктам 1 и 2; перед сдачей их нужно отправить в GitHub и получить один зелёный прогон.

- Проверка после доставки ждёт ответа сервиса циклом (до 2 минут) вместо `sleep 30` и сравнивает `/version` с commit SHA выпуска, а также проверяет сложение `2+3=5` ([ci-cd.yml](../.github/workflows/ci-cd.yml)).
- Предыдущий выпуск сохраняется на VPS: `scripts/ci-deploy.sh` перед каждой доставкой копирует `configs/.env` в `configs/.env.previous` и дописывает в `configs/releases.log` строку «время, версия, образ, предыдущий образ» ([ci-deploy.sh](../scripts/ci-deploy.sh)).
- Входные данные ручного отката проверяются (`sha256:<64 hex>`, безопасные символы версии) до любых действий на сервере ([rollback.yml](../.github/workflows/rollback.yml)).
- В образ добавлены метки OCI с commit, а в сводку прогона — готовая строка для таблицы «версия — commit — digest».
