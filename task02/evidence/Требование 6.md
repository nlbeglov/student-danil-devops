# Требование 6
## 1. Workflow отката
[.github/workflows/rollback.yml](../.github/workflows/rollback.yml) запускается только вручную (`workflow_dispatch`), с двумя обязательными полями формы: `image_digest` и `app_version`. В job'е `rollback` **нет** шага сборки — используется тот же `scripts/ci-deploy.sh`, что и в обычном деплое, но `IMAGE_REF` собирается из уже готового, ранее опубликованного digest (`ghcr.io/<repo>@<введённый digest>`), а не из нового билда. Это структурно гарантирует «откат без пересборки»: собирать образ в этом workflow просто нечем — job `build` в файле отсутствует.
## 2. Как запускали
GitHub → Actions → Rollback → Run workflow → ветка `main` → поля `image_digest` (digest нужной версии из [Требование 5](<Требование 5.md>) или лога сборки) и `app_version` (её commit SHA) → Run workflow.

| Rollback #2 | Success | https://github.com/nlbeglov/nerp-test-task02/actions/runs/35876611691 |

Точные значения, введённые в форму для каждого прогона, не видны в публичном веб-интерфейсе (логи запуска открываются только авторизованным пользователям репозитория) — это описано как ограничение в корневом `RESULT.md`. Наблюдаемый факт: после `Rollback #2` (23.09, 17:46 GMT+3) на VPS работает контейнер с digest `sha256:b764d0dcbe40...` (коммит `83a3acd`), время старта контейнера совпадает с временем прогона до секунды:
```
docker inspect --format='{{.Name}} {{.State.StartedAt}}' task02-app-1
```
```
/task02-app-1 2026-09-23T14:46:33.90836327Z
```
(14:46:33 UTC = 17:46:33 GMT+3 — совпадает со временем `Rollback #2` из истории Actions).
## 4. Проверка после отката
```
curl -s https://test0.politblocks.com/health; echo
curl -s https://test0.politblocks.com/version; echo
curl -s "https://test0.politblocks.com/add?a=2&b=3"; echo
```
```
{"status":"ok"}
{"version":"83a3acd55071798f0c6dbe84d1a3697f86bd6ed5"}
{"result":5}
```
Все три проверки, которые делает сам workflow в шаге «Verify rollback» (health, version == ожидаемому, сложение), проходят и вручную.
## 5. Порядок следующего обычного выпуска
Откат — ручная, отдельная от `ci-cd.yml` операция; для обычного релиза он не нужен. Следующий обычный выпуск делается так же, как и все предыдущие: исправить код (например вернуть `return jsonify(result=a + b)` вместо `a + b + 1`), закоммитить и запушить в `main`:
```
git commit -am "Fix off-by-one bug in addition"
git push origin main
```
`ci-cd.yml` сам прогонит тесты, соберёт новый образ с digest нового коммита, опубликует его в GHCR и задеплоит на VPS с проверкой `/health`/`/version`. `Rollback` при этом не запускается и не требуется — он существует только на случай, если после такого обычного релиза что-то пойдёт не так.
